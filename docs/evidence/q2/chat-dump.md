On Single-AZ vs Multi-AZ:

Single-AZ means your RDS database runs in one availability zone. If that AZ has a hardware failure or AWS incident, your database goes down and you have to wait for manual recovery or a restore from backup. Downtime can be 20-30 minutes or more.

Multi-AZ means AWS automatically maintains a synchronous standby replica in a second availability zone. If the primary fails, AWS automatically fails over to the standby in 1-2 minutes with no manual intervention. It costs roughly double but gives you automatic recovery.

Stage uses Single-AZ because there are no real users. If the database goes down during a test you just wait or restart. The cost saving matters more than availability in a non-production environment.

Prod uses Multi-AZ because real users are querying it during client calls and compliance reviews. A 30-minute database outage during a CNMV audit or a live client call is a serious operational failure for a regulated firm.

Claude responded: Yes, promotion flow is how code and configuration moves from dev to stage to prod.
Yes, promotion flow is how code and configuration moves from dev to stage to prod. Branching and tagging are the mechanisms that control that movement.

Branching:

A branch is a parallel version of your codebase in Git. The convention for a three-environment setup is:

main or develop branch: where developers push daily work. This is what deploys to dev automatically.
staging branch: when a feature is ready to test, you open a pull request from main into staging. Merging that PR triggers a deployment to the stage environment.
production or main branch (depending on convention): when stage has been validated, you open a pull request from staging into production. Merging triggers prod deployment.
So the branch name controls which environment gets updated. You never push directly to the production branch. Everything goes through a PR and review.

Tagging:

A tag is a named marker on a specific commit. In your project you already used this: final-vX.Y.Z with Commitizen. Tags are used to mark release points. The convention is semantic versioning: v1.2.3 where 1 is major, 2 is minor, 3 is patch.

Developer works on feature branch

When dev is stable, PR opened from main into staging, deploys to stage

Stripping PII means replacing real identifying information with fake or anonymised equivalents before copying data from prod to stage. So instead of:

## Reverse-proxy / TLS choice

In dev and stage Caddy handles reverse proxy and TLS. Caddy was chosen because it automatically provisions and renews Let's Encrypt certificates with zero configuration, integrates cleanly with DuckDNS for dynamic DNS, and has no cost. Since dev and stage have no real users there is no need for the scalability or health check features of a managed load balancer. In prod Caddy is replaced by ALB + ACM.
